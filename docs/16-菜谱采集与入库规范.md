# 菜谱采集与入库规范

## 原则与来源

只导入拥有使用许可、授权或可明确合法使用的数据。保存来源 URL/文件、作者、许可、抓取时间、原始内容哈希和采集人。尊重站点条款、robots、频率限制和版权；不绕过登录、付费墙或技术限制。来源不明或许可不清的内容只能留在待处理区，不能发布和索引。

## 状态机

`submitted → fetched → parsed → normalized → validated → review → published`；任一步可转为 `failed`，人工可转 `rejected`。发布后触发索引；索引完成才标识为 `searchable`。任务不可修改原始输入，重跑生成新的处理记录。

## 处理步骤

1. 导入 JSON/CSV/人工录入或经批准的 URL，计算 `raw_hash` 去重。
2. 提取标题、食材、步骤、时间、份量、图片、标签和来源；保留原文与解析置信度。
3. 将食材别名映射为 `ingredient`，单位转为规范单位；无法识别的字段列入人工待审，禁止模型静默猜测。
4. 执行发布校验：必填字段、步骤顺序、合理时长、食材完整性、来源许可、重复菜谱和潜在过敏原。
5. 人工审核差异、补齐标签和季节信息，发布后写入关系库并异步建立向量索引。

## 去重与质量

先以 `raw_hash` 精确去重，再以规范标题、核心食材和步骤相似度找候选重复，合并由人工决定。每次导入提供总数、成功数、待审数、失败数与逐条错误码。失败示例：`SOURCE_LICENSE_UNKNOWN`、`RECIPE_REQUIRED_FIELD_MISSING`、`INGREDIENT_UNRESOLVED`、`DUPLICATE_CANDIDATE`、`INDEX_FAILED`。

## AI 生成菜谱直接入库（手动粘贴模式）

需求：让外部 AI（如 Claude）按后端抽取 Schema 生成一份菜谱 JSON，用户通过「AI 采集入库 → 手动粘贴」提交，抽取零误差、直接进待审候选。手动模式会自动识别粘贴内容：

- **结构化菜谱 JSON（AI 生成）** → 直接校验落库，**跳过 LLM 抽取**，来源 URL 可留空；
- **网页正文**（登录墙/反爬站点如小红书）→ 走 `extract_recipe_with_fix`（`RecipeExtraction` schema，见 `backend/app/llm/prompts.py`）对粘贴正文抽取一遍。

因此**结构规整的 JSON 最可靠**；普通完整菜谱文字（含菜名+食材+步骤）也能入库，但需填来源 URL，且抽取结果可能不稳。

### 提示词（复制即用）

> 你是专业的菜谱编写与整理助手。请根据我提供的菜谱要求（菜名/食材/参考来源），给出**一份完整、可直接入库的菜谱**，输出为一个合法的 JSON 对象。只输出 JSON，不要任何解释或多余文字（若用 ```json 代码围栏也会被自动识别）。
>
> 字段规则：
> - `title`：菜名，必须非空
> - `summary`：一句话简介（可选）
> - `servings`：份量，整数（可选）
> - `prep_minutes` / `cook_minutes`：准备/烹饪时间，分钟，整数（可选）
> - `difficulty`：只能是 `简单` / `中等` / `困难`
> - `ingredients`：食材列表，**不含调料**，每项 `{"name":"食材名","amount":"用量如2个/3克/适量","preparation":"处理方式如切丁，可选"}`
> - `seasonings`：调料列表，盐、糖、生抽、老抽、料酒、醋、蚝油、花椒、八角、葱姜蒜、淀粉等调料/香料/酱汁放这里，格式同食材
> - `steps`：步骤列表，每项 `{"step_no":序号,"instruction":"这一步的具体做法","duration_minutes":分钟，可选}`，从 1 递增
> - `tags`：标签数组，如 `["家常菜","快手菜"]`
>
> 硬性要求：
> 1. 菜名非空、食材至少 1 条、步骤至少 1 条，否则无法入库；
> 2. 用量写具体（`2个`/`3克`/`适量`），**不要编造**来源里没有的用量和步骤；
> 3. 调料与食材严格分开，不要把盐/生抽混进 ingredients；
> 4. 步骤按真实烹饪顺序排列，覆盖备料到出锅。
>
> 输出示例：
> `{"title":"西红柿炒鸡蛋","summary":"经典家常菜","servings":2,"prep_minutes":5,"cook_minutes":10,"difficulty":"简单","ingredients":[{"name":"西红柿","amount":"2个","preparation":"切块"},{"name":"鸡蛋","amount":"3个","preparation":"打散"}],"seasonings":[{"name":"盐","amount":"适量"},{"name":"葱花","amount":"少许"}],"steps":[{"step_no":1,"instruction":"西红柿切块，鸡蛋加少许盐打散"},{"step_no":2,"instruction":"热油炒熟鸡蛋盛出，再炒西红柿出汁后回锅","duration_minutes":5},{"step_no":3,"instruction":"加盐调味，撒葱花出锅"}],"tags":["家常菜","快手菜"]}`
>
> 现在请根据【菜名/食材/要求】生成菜谱。

### 结构化 JSON 直入路径

粘贴内容被识别为结构化菜谱 JSON 时（`ai_collection_service._try_parse_structured_recipe`），后端**不调 LLM**、直接校验落库为待审候选：

- **检测规则**：去首尾空白与 BOM → 兼容 ```json 围栏（大小写不敏感）→ 严格 `json.loads` → 顶层为对象且 `title`（去空白后）非空。前后端用同构逻辑；前端 `JSON.parse` 更严（拒绝 NaN/Infinity），只会让用户多填来源 URL，判定漂移仅发生在安全方向。
- **URL 可选**：结构化 JSON 菜谱可留空来源 URL；非 JSON 网页正文仍需来源 URL（`create_ai_job` 校验）。
- **校验失败不回退 LLM**：如 `{"title":"x"}`（有标题无食材）→ 直接 `EXTRACTION_FAILED` 并记录原因（"无食材"），避免把 JSON 文本丢回 LLM 掩盖 schema 不匹配。
- **来源来源**：JSON 自带 `source_url` 可作为候选来源，但仅接受 `http://`/`https://`（防 `javascript:` 注入）。
- **不依赖 LLM**：LLM 宕机时结构化 JSON 仍能进待审；超长内容（>200k 字符）放弃直入回退 LLM 截断路径。
- 超长/病态粘贴由 `_MAX_STRUCTURED_JSON_CHARS` 上限兜底。

### 使用注意

1. **URL 可选**：粘贴结构化菜谱 JSON 时可留空来源 URL（自动识别）；粘贴网页正文（非 JSON）时仍需来源 URL（`ai_collection_service.create_ai_job` 校验）。有真实来源填链接；纯创作无来源时用「手动粘贴」贴 JSON 即可入库。
2. **入库路径**：手动粘贴 → 提交总结 → 待审候选 → 确认入库。确认后菜谱才正式发布并触发索引（`review_candidate` approve）。
3. **校验规则**：与后端 `validate_recipe_reason` 一致——标题非空（含空白标题拒绝）、至少 1 食材、至少 1 步骤；调料词典（盐/酱油/料酒/葱姜蒜等）命中会自动从 ingredients 拆到 seasonings。
