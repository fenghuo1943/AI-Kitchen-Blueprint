# 开发流程

每个可交付功能遵循：

1. 阅读 `docs`，确认 PRD、ADR、数据、API 与边界；有架构影响先提出 ADR。
2. 在 `14-TODO` 记录范围、验收条件、依赖和风险，拆分为一个可测试模块。
3. 先定义领域模型、接口/Schema 和测试案例，再实现后端、前端或任务适配。
4. 本地执行格式化、静态检查、单元及相关集成测试；手工走通主路径和失败路径。
5. 更新迁移、OpenAPI、Prompt/评分版本、文档和 TODO 历史；记录已知限制。
6. 评审时检查数据来源许可、隐私、可观测性、降级和向后兼容性。

不得在一个变更中夹带无关重构。第三方依赖、新模型、数据源、外部 API 与数据库破坏性变更均需说明理由、版本、回滚/降级方式。完成定义（DoD）：代码、测试、文档、配置示例和验收证据齐全。

## 标准开发流程

每个功能都应按以下顺序完成：

1. 先理解需求与边界：阅读 PRD、ADR、数据字典与相关规范，确认是否涉及架构变化。
2. 先定义验收条件：明确“输入、输出、失败场景、成功场景”和可验证证据。
3. 先定义接口与数据结构：先编写 Schema、迁移草案、测试用例，再开始实现。
4. 再实现核心逻辑：领域逻辑优先写成可测试的服务或纯函数，避免把业务规则散落在路由层。
5. 再补测试与验收：单元测试覆盖规则，集成测试覆盖 API 与任务，必要时补手工验收记录。
6. 最后更新文档与变更说明：任何 API、Prompt、评分或数据模型变更都必须同步更新文档与版本信息。

## 完成定义

一个功能完成的标准是：

- 代码已实现
- 单测或集成测试已通过
- 文档已更新
- 配置示例已补齐
- 验收证据已记录
