# 实施路线图

## 目标

将当前方案从设计说明推进为可执行的 MVP 开发路线，确保项目能够按阶段落地并形成可验证结果。

## 交付目标

1. 建立可管理的菜谱知识库，支持草稿、审核、发布与版本管理。
2. 提供规则驱动的推荐能力，基于库存、季节、目标和时长返回可解释结果。
3. 支持本地可用能力：无云模型时仍能完成浏览、库存和规则推荐。
4. 为前端、RAG 和采集任务提供稳定的 API 与数据契约。

## 阶段安排

### Phase 0：工程基线

目标：搭建可持续开发基础。

交付物：
- 后端与前端骨架目录
- 配置管理、日志与健康检查
- 数据库迁移脚本与测试数据
- 格式化、静态检查与测试脚手架

### Phase 1：知识库与入库

目标：建立可被推荐和检索的菜谱知识源。

交付物：
- 食材规范化与别名映射
- 菜谱草稿/审核/发布流程
- CSV/JSON/人工录入入库任务
- 发布后索引与任务状态管理

### Phase 2：库存与推荐

目标：让用户从库存与约束条件中获得候选菜谱。

交付物：
- 库存 CRUD 与保质期提醒
- 硬约束过滤、覆盖率和缺料计算
- 推荐理由展示与解释输出

### Phase 3：RAG 问答与 AI 增强

目标：让 AI 作为解释器与辅助助手，而不是知识来源的替代者。

交付物：
- 基于已发布菜谱的问答接口
- 证据引用、拒答与降级策略
- 本地模型接入与结构化输出校验
- 响应式设计（移动端、平板端、桌面端自适应布局）

### Phase 4：发布准备

目标：让系统具备可交付和可运维能力。

交付物：
- 权限与审计机制
- 备份、恢复与数据导出流程
- 性能、隐私与可访问性验收记录
- 部署与运维手册

## 实施原则

- 先实现规则和结构化数据，再引入 AI 解释。
- 所有推荐结果必须可追溯到菜谱、食材或标签数据源。
- 入库和发布流程必须保留人工审核与审计能力。
- 模型调用必须具备超时、降级与日志记录。
