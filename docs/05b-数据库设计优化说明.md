# 数据库设计优化说明

## 目标

基于现有的 legacy 数据库结构与已完善的文档规范，构建一个更适合 AI 菜谱知识库、菜谱推荐、库存管理和异步入库流程的数据库设计。

## 设计思路

1. 保留原有菜谱内容库的语义基础，同时新增面向现代 AI 应用的结构化实体。
2. 将“菜谱事实”与“AI 检索/推荐”分层管理：
   - 关系表保存权威菜谱事实。
   - 向量索引表仅保存检索映射，不保存权威数据。
3. 将“草稿、审核、发布、归档”状态流转显式建模，便于入库与审核流程。
4. 将库存、采集任务、审计日志单独抽象，便于扩展和追踪。

## 设计原则

- 关系数据为权威来源，向量数据为补充索引。
- 所有业务表保留审计字段与软删除字段。
- 关键字段使用规范命名，避免混用旧式命名风格。
- 推荐和 RAG 相关逻辑优先依赖结构化字段，而不是纯文本。

## 关键表说明

### 1. households
用于支持家庭级库存与场景隔离。MVP 中可只使用一个默认家庭。

### 2. ingredients / ingredient_aliases
统一管理食材规范名与别名，便于做库存匹配、推荐过滤和语义召回。

### 3. recipes / recipe_revisions
菜谱主表与修订表分离，支持版本管理，已发布版本不可直接覆盖。

### 4. recipe_ingredients / recipe_steps / recipe_tags
构建菜谱的结构化成分、步骤和标签，供推荐和检索使用。

### 5. inventory_items
支持家庭库存管理，包含数量、单位、过期时间和备注，适配推荐和保质期提示。

### 6. ingestion_jobs
记录采集/导入任务的状态、阶段和失败原因，适配异步重试与审计。

### 7. document_chunks
保存菜谱的切块信息与向量映射，供 RAG 检索使用。

### 8. recommendation_logs
记录脱敏后的推荐请求与候选结果，便于评估和优化排序策略。

### 9. audit_events
记录关键业务动作，支持审计和回溯。

## 与原有 cookbook.sql 的关系

原有 `cookbook.sql` 主要是传统内容库结构，适合保留其内容和分类字段语义；新的优化设计则是面向 AI 家庭厨房助手的增强层，重点补齐：
- 食材规范化
- 库存和过期管理
- 菜谱状态流转
- 推荐与 RAG 需要的结构化字段
- 入库任务的可追踪性

## 建议落地方式

- 新项目优先使用新表结构，避免直接把业务逻辑绑定在老表风格上。
- 旧表可作为迁移兼容层，逐步映射到新结构。
- 对于 MVP，优先实现以下核心表：
  - `ingredients`
  - `recipes`
  - `recipe_ingredients`
  - `recipe_steps`
  - `inventory_items`
  - `ingestion_jobs`
  - `document_chunks`

## 推荐的初始迁移顺序

1. `households`
2. `ingredients` / `ingredient_aliases`
3. `tags`
4. `recipe_sources`
5. `recipes` / `recipe_revisions`
6. `recipe_ingredients` / `recipe_steps` / `recipe_tags`
7. `inventory_items`
8. `ingestion_jobs`
9. `document_chunks` / `recommendation_logs` / `audit_events`
